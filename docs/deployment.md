# 部署與回復

狀態：未執行；M0 不產生安裝 ZIP、不登入正式站。

## M1/M2 隔離驗證

先建立示範站；UR 副本必須與正式站資料庫、網域、憑證及 API 設定隔離。匯入前處理個資、寄信、排程及付費 API，確認禁止索引與存取限制。保存測試基準與還原方式。

原生操作：上傳 Core ZIP → 啟用 → 外觀／編輯器／樣式 → 選擇配色 → 儲存。檢查十套配色、單色及字型調整、切換、重設。WordPress 介面標籤若依版本不同，文件隨實測更新。

配色更新前備份資料庫及自訂樣式，記錄當前版本、配色及修改；先在副本試用新版。使用原生介面重新套用會改動樣式，不能承諾保留所有個人修改。首版採人工核對，匯入、匯出與差異合併工具留後續。

## M3 發布

通過檢查後使用語意化版本，輸出 ZIP、SHA-256、檔案清單、變更說明、已測環境與已知限制。保留前一版 ZIP。GitHub Release 需先建立遠端及發布流程，本輪不發布。

## 未來正式切換

另行具體確認部署範圍及授權；先備份檔案與資料庫，驗證可還原，盤點測試期間新增資料。部署後清快取，檢查首頁、文章、搜尋、表單、AI、會員及錯誤日誌。

嚴重錯誤時先回復本次佈景／外掛及設定；檔案回退不會還原 DB 樣式。需要還原資料庫時先保護備份後新資料，不用舊測試資料庫覆蓋正式站。記錄原因、影響、回復結果與未解決問題。

## 更新機制：現在沒有，而且建議先不要做

佈景目前沒有任何更新通知。`style.css` 只有版本號，沒有 `Update URI`，
所以裝上去的站不會知道有新版——要更新只能手動上傳 ZIP。

### 做得到，但沒有官方管道

WordPress 的自動更新 UI 綁的是 wordpress.org。私人佈景走不了那條，有三個選項：

| 做法 | 怎麼運作 | 代價 |
| --- | --- | --- |
| `Update URI` + `update_themes_{$hostname}` filter | 在 style.css 指向自己的網址，由 filter 回傳版本與 ZIP 位置 | 要自己維護一個端點；端點掛掉就沒人收到更新。這是最接近官方的做法——WordPress 自己的開發者筆記承認外部託管沒有官方方法，但這個 hook 是為它設計的 |
| Git Updater 之類的外掛 | 讓外掛直接從 GitHub repo 讀版本 | 每個站多一個外掛；私人 repo 要把 token 放到各站上，三個站就是三份憑證 |
| 不做，手動 ZIP | 現在的做法 | 三個網站的規模還不算負擔，而且每次更新都會親眼看到自己在改什麼 |

### 🚩 真正的難處不是送檔案

[architecture.md](architecture.md) 已經寫過：使用者在網站編輯器儲存的樣式優先序高於檔案，
資料庫裡的模板修改也可能遮蔽新版檔案。所以**更新佈景檔案不等於網站外觀跟著變。**

對共用佈景這是真問題。假設把某個配色的主色改深一點，三個站都更新了——
其中一站的管理員之前在網站編輯器手調過顏色並儲存，那一站就不會變，
而且不會有任何提示。你以為三站一致，實際上是二比一。

本文件上面已經寫了「不能承諾保留所有個人修改」，但沒寫**怎麼知道哪個站偏離了**。
那是缺的那一塊。

### 所以順序是

1. 先讓「這個站跑哪一版、有沒有被手改過」看得出來。
   版本常數 `FUTHEME_CORE_VERSION` 已經有了；還缺一個能列出資料庫裡
   存了哪些 Global Styles 覆寫的小工具。有了它才知道一次更新推下去會發生什麼。
2. 等第一個網站真的裝上去、配色切換也驗過之後，再決定要不要自動更新。

沒有第一步就做自動更新，等於把「不知道結果」這件事做得更快。

而且照目前狀況這還排不到前面：FuTheme 連一個確定的採用者都還沒有
（見 [採用狀態](adoption.md)），配色能不能在後台切換也還沒驗
（見 [專案狀態](status.md)）。
